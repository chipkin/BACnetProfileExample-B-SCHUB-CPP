## Goal

`C:\dev\chipkin\cas-bacnet-stack-examples\BACnetProfileExample-B-SCHUB-CPP` (also
https://github.com/chipkin/BACnetProfileExample-B-SCHUB-CPP) is a BACnet/SC (Secure Connect) Hub
example built on the CAS BACnet Stack. Today its BACnet/SC **protocol** support is real and
stack-verified, but the **transport** (WebSocket + TLS) is an honest stub: the callbacks the stack
uses to ask the host to open/accept connections just log what was asked and decline. The goal is
to replace that stub with a real, working WebSocket+TLS transport so that a genuine external
BACnet/SC node or hub can connect to (and, for the outbound role, be connected to by) this
example over the wire — "the full example a customer would expect when connecting to a BACnet/SC
Hub."

## What a B-SCHUB hub function minimally needs to do (verify this yourself against the manual, don't just trust this summary)

1. A real `wss://` listener bound to the configured accept URI(s) — currently
   `wss://0.0.0.0:47819/` (see `main.cpp`'s SC setup section) — negotiating TLS 1.3 with mutual
   authentication and the `hub.bacnet.org` WebSocket subprotocol (confirmed name via the sibling
   client's working implementation; cross-check against ASHRAE 135-2024 Annex AB.7.1 or the SC
   manual if you can find it stated there directly).
2. Per accepted connection, relay raw binary WebSocket frames between the app's
   `RegisterCallbackReceiveMessage`/`RegisterCallbackSendMessage` and the stack — the stack itself
   owns all BVLC-SC framing, VMAC assignment/collision handling, and inter-node forwaring logic
   (confirmed "Complete" in the manual's own Appendix G conformance table); the app must NOT
   reimplement any of that.
3. Call `BACnetStack_SetBACnetSCWebSocketStatus()` on every real connect/disconnect/error, per
   connection/URI.
4. Everything async/non-blocking — the transport callbacks fire from inside `BACnetStack_Tick()`
   and must not block it.
5. A working certificate story (see below) — without a loaded operational cert + key + trusted CA
   in the app's own TLS context, no real TLS handshake can complete regardless of how correct the
   WebSocket code is.

## Certificate handling — key facts to design against

- The stack (as of this v6 pin) does **not** store certificate bytes itself — only File-object
  *references*. `BACnetStack_SetBACnetSCCertificateFileObjects()` binds a SC Network Port to File
  objects for: the operational certificate, a CSR, and **exactly 2** issuer-certificate slots.
- The app must create these File objects (`BACnetStack_AddFileObject`) and implement
  `RegisterCallbackReadFile`/`RegisterCallbackWriteFile` to serve/accept the real PEM bytes from
  wherever the app stores them (this example should use plain files on disk, generated by the new
  setup script).
- **Separately**, the app's own TLS library (libwebsockets' OpenSSL backend) must be pointed at
  the same cert/key/CA file paths directly at context-creation time — the File objects are for
  BACnet-visible certificate *management* (an operator reading/rotating a cert over the wire via
  ReadProperty/WriteProperty/AtomicWriteFile), not what the TLS handshake itself consults. Both
  paths need to agree on the same underlying PEM files.
- `RegisterCallbackValidateBACnetSCOperationalCertificate` and
  `RegisterCallbackGenerateBACnetSCCertificateSigningRequest` exist in the header but are **not
  actually called by this stack build** (confirmed: no call site exists anywhere in the stack
  source for either). Register them for completeness/documentation purposes only; do not treat
  them as a real security control, and say so explicitly in any docs you write.
- Self-signed is explicitly sanctioned for this use case — the manual's Appendix B is titled
  "Generating Self-Signed Test Certificates with OpenSSL," gives a full CLI recipe (ECDSA P-256:
  generate a CA key+cert, generate a device key+CSR, sign the device cert with the CA, producing
  `ca.crt`/`device.crt`/`device.key`), and says outright "Production deployments must use a real
  CA." The new setup script for this example should follow this recipe (or something equivalent),
  producing files this example's `RegisterCallbackReadFile`/libwebsockets context both consume,
  and should NOT be committed into git — generate at build/setup time, gitignore the output.
